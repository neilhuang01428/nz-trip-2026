    0. 這個網站在解決什麼問題

    規劃一趟長天數自駕旅行，痛點不是「找不到景點」，是：

    痛點這個架構怎麼解
    資料散在十幾個分頁與截圖裡單一資料源 places.json，所有分頁都從它生成
    不知道某個點順不順路每個地點綁 day，按日期篩選就只留那天路線上的
    同行者看不懂為什麼這樣排行程頁把每天的方案 A/B/備案攤開，可以切換比較
    網路資訊過期、被內容農場抄爛查證紀律：只寫查得到官方出處的，查不到就明說
    到了現場才發現公休／過季／已歇業這類警告優先於推薦，用 ⚠️ 標在卡片正面
    手機上難用手機優先設計，觸控目標 ≥44px，離線可用

    核心設計原則：誠實 > 完整 > 好看。 查不到就寫「查不到」，比編一個看起來完整的答案有用得多。

    1. 技術架構

    1.1 整體

    純靜態網站，無框架、無建置工具鏈、無後端。
資料（JSON） ─┐
樣板（HTML） ─┼─→ _build.py ─→ 根目錄的 *.html（可直接開、可丟 GitHub Pages）
樣式（CSS）  ─┤
程式（JS）   ─┘

    為什麼不用框架：旅程網站的生命週期是幾個月，要能十年後還打得開。 單一 HTML 檔（CSS 與 JS 都 inline）可以用 file:// 直接開，飛機上也能看。

    1.2 檔案結構

    專案根目錄/
├── _build.py              組裝器：把樣板的佔位標記換成共用資源
├── _check.py              產出後的整站檢查（必跑）
├── _nz-style.css          全站樣式（build 時 inline 進每一頁）
├── assets/app.js          全站前端邏輯（build 時 inline 進每一頁）
├── _src/*.html            分頁樣板（要改內容改這裡，不要改根目錄的產出）
├── data/
│   ├── places.json        ★ 唯一資料源：所有地點、行程日、路線方案
│   ├── culture.json       文化與背景卡片
│   ├── talk.json          當地語言與實用會話
│   └── routes-geo.json    build 前用 OSRM 預先算好的道路幾何
├── images/
│   ├── *.jpg              照片（全部本地化，不外連）
│   ├── credits.json       每張圖的作者與授權
│   └── CREDITS.md         人類可讀的授權表
├── _geocode.py            用 Nominatim 補地點座標
├── _routes.py             用 OSRM 算路線幾何
├── _merge_*.py            把研究 agent 的產出併回資料源
└── *.html                 產出（不要手改）

    1.3 build 的運作方式

    _build.py 把樣板裡的佔位標記換成實際內容：

    標記換成什麼
    <!--NZCSS-->_nz-style.css 全文，包在 <style> 裡
    <!--NZJS-->assets/app.js 全文，包在 <script> 裡
    <!--PLACES-->data/places.json，包在 <script type="application/json"> 裡
    <!--CULTURE-->data/culture.json
    <!--TALK-->data/talk.json
    <!--ROUTESGEO-->data/routes-geo.json
    <!--NAV-->桌機頂部導覽列（自動標出目前頁）
    <!--TABBAR-->手機底部分頁列 ＋「更多」選單
    <!--LEAFLET-->Leaflet 的 CDN 標籤（含 SRI）

    指令：python3 _build.py（全部）或 python3 _build.py _src/eat.html（單頁） 改完一定要跑 python3 _check.py，它會查 id 重複、內文標籤、缺圖、未替換的標記、孤兒圖片、無授權記錄的圖片。

    1.4 外部依賴（全部免金鑰）

    用途服務注意事項
    地圖Leaflet 1.9.4 + OpenStreetMap 圖磚必須標示 OSM 貢獻者；不可大量下載圖磚
    導航連結Google Maps URLs API不需金鑰。/maps/search/?api=1&query= 與 /maps/dir/?api=1&origin=&destination=&waypoints=
    座標補齊Nominatim1 秒 1 次，要帶自訂 User-Agent，限定國別
    道路幾何OSRM demo serverbuild 時跑一次存成 JSON，執行時完全不依賴
    發音瀏覽器內建 SpeechSynthesis離線可用，不需金鑰
    圖片Wikimedia Commons只用 CC0／CC BY／CC BY-SA，作者與授權要記進 credits.json

    做不到的事（不要嘗試）：

    • 沒有 API 可以寫入 Google Maps 的「已儲存清單」。所謂「一鍵加入清單」不存在，最多是「開啟地點頁 → 使用者自己按儲存」（兩個動作）。
    • Google 評分無法免費即時取得。官方途徑是付費的 Places API，爬 Google Maps 違反服務條款。本站的評分是查證當下的快照，欄位帶 asof 查證年月與 src 來源網址。

    3. 分頁架構

    分頁內容資料來源
    總覽封面、分頁入口、全部地點的總地圖、幾個先知道的重點places.json
    景點分類 sight 的卡片 ＋ 地圖 ＋ 篩選 ＋ 搜尋places.json
    吃的分類 eat，特別標公休日與季節places.json
    需預約分類 book，標出「一定要先訂」的places.json
    重頭戲（可 0–N 頁）這趟最重要的活動，各自獨立成頁，含廠商比較、天候備案places.json ＋ 樣板內容
    文化與背景讓體驗加分的知識卡片culture.json
    開口講當地語言、地名發音、路上的標語、實用會話，可朗讀talk.json
    行前注意天氣、穿什麼、打包清單（可勾選）、開車規則、入境樣板內容
    行程安排逐日一覽 ＋ 有選擇的日子的方案切換 ＋ 路線圖places.json 的 routes

    分頁數量可以增減，但這幾件事建議保留：

    1. 主題分頁 ＋ 地圖 ＋ 日期篩選這組合是核心
    2. 行程頁放方案比較，不要把選擇藏在文字裡
    3. 行前頁是實用價值最高的一頁，不要省
    4. 重頭戲獨立成頁——最貴、最看天氣的活動值得一整頁講清楚

    4. 核心功能

    功能說明
    日期篩選選某一天，只留那天路線上的地點。選了會顯示那天的行程摘要
    條件篩選必去／要預約／免費／隱藏已歇業
    關鍵字搜尋多關鍵字 AND，命中反白，比對範圍含展開後的內文
    清單／地圖切換手機是全螢幕地圖面板，桌機是上下並排
    卡片 ↔ 地圖雙向連動點卡片的「在地圖上」會捲到地圖並開 popup；點 pin 會反白卡片
    卡片展開「知道了會不一樣」的深度知識，沒特別可講就不顯示這一塊
    外幣自動換算內文出現當地幣別時，自動在旁邊加上母語幣別估算
    訂位連結官網 ／ 第三方平台（Klook、KKday…）分開列
    發音朗讀用瀏覽器內建語音，離線可用；另附真人發音的外部連結
    打包清單可勾選，狀態存在 localStorage
    路線圖build 時用 OSRM 算好道路幾何，執行時不依賴外部 API

    5. 設計系統

    5.1 色彩

    用當地的顏色當主色，不要用通用配色。本站取自紐西蘭：

    --pukaki:  #3E9DB8   /* 冰河湖的藍 */
--pounamu: #1F5B4E   /* 綠玉的綠 */
--tussock: #C08A3E   /* 高原草原的金 */
--kowhai:  #E5B23C   /* 國花的黃 */
--rata:    #BE3B2B   /* 原生樹的紅 */
--night:   #0B1620   /* 暗空保護區的夜 */

    換一個目的地時，重新挑一組屬於那裡的顏色。這是整個網站個性的來源。

    5.2 字體

    • 標題：襯線體（本站 Cormorant Garamond）
    • 內文：無襯線 ＋ 中文字體（Inter + Noto Sans TC）
    • 數字／代號：等寬字，並開 font-variant-numeric: lining-nums tabular-nums

    5.3 「這個可以點」的設計紀律（吃過虧的經驗）

    使用者連續回報四次「不知道這個可以點」。歸納出的順序是：

    文字 > 圖示 > 顏色
    • 可展開的區塊：右側放一顆寫著「展開／收合」的膠囊，不要只放一個小箭頭
    • 可橫向捲動的列：邊緣漸層 ＋ 可按的箭頭 ＋ 尾端留白 ＋ 首次進入輕晃一次
    • 會發出聲音的鈕：圖示旁邊加「聽」字，播放中換成「播放中」
    • 一組擇一的選項：加單選圓點（○/●）＋「點這裡看／✓ 目前看這個」的狀態文字，並用 role="radiogroup"
    • 導覽列：把分頁包在一條有底色的軌道裡，讀起來才像「一組可切換的東西」
    • 每個可互動元素都要有 :hover、:active、:focus-visible 三種狀態
    • 手機觸控目標 ≥44×44px

    5.4 手機優先

    預期八成流量在手機。底部固定分頁列、清單／地圖切換、篩選晶片橫向捲動、 輸入框字級 16px（避免 iOS 自動放大）、env(safe-area-inset-bottom)。

    6. 內容品質規則（最重要的一節）

    這是這個網站跟一般旅遊部落格最大的差別。照抄這些規則。

    6.1 查證紀律

    1. 優先官方來源：政府機關、國家公園管理單位、業者官網、法定資料庫。
    2. 內容農場互相抄襲且常錯。 至少兩個獨立可信來源一致才採用。
    3. 查不到出處就不要寫。 寧可少寫，不要編。
    4. 保留語氣是刻意的：「一般認為」「有幾種說法」「查不到出處」「這是傳說不是正史」「官方未如此宣稱」——這些字眼寫進去之後，後續任何改寫都不可以拿掉，拿掉就變成假訊息。
    5. 有爭議的說法要並列，不要挑一個當定論。
    6. 每一頁的頁尾要有「這些我查不到」一節，明列沒有官方依據的項目。

    6.2 警告優先於推薦

    實際查證過程中，最有價值的產出往往是否定的：

    • 「這家店 2023 年已經永久歇業，但中文資訊還在推薦」
    • 「這個裝置藝術已經被藝術家撤除了」
    • 「這個海鮮 10 月完全過季」
    • 「這條步道 10/01–11/10 因產羔羊封閉」
    • 「這個景點的常見說法是錯的」

    這類資訊一律用 ⚠️ 標在卡片正面，並且在任何後續改寫中都不可以削弱力道。

    6.3 反翻譯腔

    用當地語言查資料、用母語寫給讀者看，很容易寫出「翻譯感很重」的句子。檢查清單：

    症狀例子
    「X 不是 A，是 B」句式濫用，而且 A、B 不成對比「『你跟誰講了？』在這裡不是嘮叨，是制度。」
    反問句開頭卻沒回答同上
    抽象名詞硬當主詞「深水物種淺化」「行程意向」
    副詞配形容詞的怪組合「原因很物理」「白話到近乎樸素」
    外語直譯Gore 地區「乾」了 51 年（dry ＝ 禁酒，不是氣候）
    專有名詞未解釋就使用「根瘤蚜」「砧木」
    「的」連續堆疊「一場打了一百五十年的官司的結果」
    無效形容「令人驚豔」「不容錯過」「美不勝收」

    好的寫法：具體 > 抽象、短句 > 長句、一句話講一件事。 與其說「地質作用造就獨特景觀」，不如說「那個藍是石頭磨成的粉」。

    6.4 改寫時的紅線

    用 AI 改寫文案時，每一筆都要驗證後才寫入，任何一項不過就整筆退回：

    • 數字集合完全一致（年份、金額、公里數、營業時間）
    • 當地語言的特殊字元一致（例如毛利語的長音符號 ā ē ī ō ū）
    • ★／⚠️／❌ 等標記數量一致
    • 保留語氣詞（6.1 第 4 點那些）沒有消失
    • HTML 標籤配對且只允許 <b>
    • 段落數不變

    本站的 _merge_rewrite.py 就是在做這件事，它真的攔截到過改壞的內容。

    7. 工作流程

    7.1 從零到上線

    1. 問清楚需求（見第 8 節的問題清單）
2. 建 data/places.json 的 meta（行程日、分類、匯率）
3. 分區派研究 agent 蒐集地點 → 併回 places.json
4. python3 _geocode.py   補座標（Nominatim，1 秒 1 次）
5. 人工抽查座標（跨城鎮距離異常的要抓出來）
6. python3 _routes.py    算路線幾何
7. 抓圖片 → 壓縮 → 記錄授權
8. python3 _build.py && python3 _check.py
9. 手機／桌機各量一次版面（用無頭瀏覽器量 getBoundingClientRect，不要只看截圖）
10. commit + push（公開版建議另開一個只放產出的 repo）

    7.2 用 subagent 平行處理

    適合平行的：分區蒐集資料、分區查證、獨立的唯讀稽核。 不適合平行的：多個 agent 改同一個檔案——會互相覆蓋。真的需要就用 git worktree 隔離。

    有效的做法：

    • 一個 agent 只負責一個地理區域或一個主題
    • 給它明確的輸出 JSON 格式與輸出檔路徑
    • 要求它回報「查證後推翻或不敢寫的說法」——這部分往往比正面成果更有價值
    • 另外派一個唯讀稽核 agent，用無頭瀏覽器實際量測介面問題

    7.3 驗證要用量的，不要用看的

    無頭瀏覽器截圖有陷阱（最小視窗寬度、捲動位置、動畫不執行），多次被誤判成 bug。 可靠做法是注入腳本、用 getBoundingClientRect() / getComputedStyle() / elementFromPoint() 量， 把結果塞進 document.title 再用 --dump-dom 撈出來。 要模擬真實手機寬度（無頭最小 500px），用 iframe 強制 390×844，並加 --allow-file-access-from-files。

    8. 給 AI：開工前要先問使用者的事

    在寫任何一行程式碼之前，先問清楚這些。 沒問清楚就開始做，後面幾乎一定要重來。

    8.1 必問（沒有答案就無法開始）

    1. 去哪裡？ 國家／地區／大致路線。是環線還是單程？
    2. 哪天出發、哪天回來？ 含班機時間——這會決定第一天和最後一天實際能用多少時間。
    3. 幾個人？ 大人小孩、體力狀況、有沒有行動不便的。
    4. 怎麼移動？ 自駕（什麼車）／大眾運輸／包車。自駕的話有沒有人不能開夜車。
    5. 住宿訂了嗎？ 哪幾晚已經訂死不能改？（這是最強的約束條件，會鎖住整條路線）

    8.2 幾乎一定要問

    1. 有沒有已經訂好、不能改的行程或活動？（跳傘、遊船、演唱會、餐廳訂位…）
    2. 這趟最想做的一到三件事是什麼？ 這些值得獨立成頁，並且要規劃天候備案。
    3. 住宿等級與預算感覺？（不用精確數字，「舒適三四星」這種就夠）
    4. 飲食限制？ 素食、過敏、不吃某樣東西、宗教限制。
    5. 體力偏好？ 想每天健行，還是以開車看風景為主？可以接受單日開多久車？

    8.3 會大幅改變結果的細節

    1. 同行者的裝置是 iOS 還是 Android？（影響地圖方案與離線建議）
    2. 要不要把「同行者的願望清單」納入？ 如果有，怎麼收（Google Maps 清單匯出、截圖、口頭）。
    3. 有沒有特別在意的東西？ 星空、野生動物、酒莊、鐵道、建築、特定電影取景地。
    4. 語言？ 當地講什麼語言，需不需要做「開口講」那一頁。
    5. 這份網站要給誰看？ 只有自己看，跟要說服同行者，內容取捨完全不同。

    8.4 開始做之後仍要確認的

    1. 某天行程明顯過重（例如純開車 7 小時以上）時，要主動提出並給修正方案，不要照抄使用者的原始想法。
    2. 遇到「查證後發現使用者的假設是錯的」時（例如某地點已歇業、某活動不在該季節），要明確講出來，不要默默改掉。
    3. 版本控制：要不要 commit？要不要公開？公開的話個資（訂位代號、電話、住宿地址）要不要拿掉？

    坑說明
    座標會歪很遠Nominatim 曾把一個地點放到 236 公里外。一定要做「地點到所屬城鎮的距離」異常檢查
    圖片名稱會騙人Wikimedia 上學名正確的檔案，內容可能是別的東西（查到一張「奇異鳥」其實是苔蘚上的幾根羽毛）。用之前一定要看過
    無頭瀏覽器截圖會誤導最小視窗 500px、捲動位置不生效、behavior:'smooth' 不動畫、程式化捲動不觸發 scroll 事件。用量測不要用目測
    width:100% + 左右 margin在 border-box 下仍會超出容器，要用 calc(100% - 兩側 margin)
    grid/flex item 的 min-width:auto會被子孫的 max-content 撐開，導致整頁橫向溢出。加 min-width:0
    [hidden] 會被 display:flex 壓過要另外寫 .xxx[hidden]{display:none}
    opacity:0 仍然可以點要一起加 pointer-events:none 或用 visibility:hidden
    CSS 選擇器寫 a.on 但元素是 button造成六個分頁的底部導覽完全沒有選取狀態
    scroll-snap 會把捲動位置吸回去讓「按箭頭捲動」看起來沒作用
    多個 agent 改同一個檔案後寫的會蓋掉先寫的。要嘛排隊，要嘛用 worktree
    AI 改寫文案會順手改壞事實一定要寫驗證器擋，不要相信「我有注意保留」
    搜尋引擎會整批擋掉你這輪四個 agent 同時撞牆：Google／Bing／DDG／Yandex／Startpage／Mojeek／Ecosia／Brave 全部 CAPTCHA 或 403，Tripadvisor／Viator／Klook 整站 403。是出口 IP 被反爬蟲擋，不是查詢技巧問題。能通的替代路徑：業者官網內嵌的 schema.org AggregateRating、聚合站頁面內嵌的 JSON（例如 wanderlog 的 __MOBX_STATE__ 直接帶 Google 的 rating／numRatings／permanentlyClosed）、地區性評論站
    AI 給的數字要驗「像不像真的」請外部 AI 代查評分時，它回的評論數 66% 是 50 的倍數（實際解析頁面拿到的只有 3%）——統計上不可能，代表是估算值。星等倒是準。處理方式：實測優先、外部 AI 只補空缺並標記為估算，畫面上顯示「約 2,400」
    同一個地點會被兩個 agent 各收一次分區蒐集時邊界地點（例如同時在去程與回程路上的小鎮）會重複。用「同名 ＋ 座標 350 公尺內」自動抓，但名稱包含關係要加長度門檻，否則「Glenorchy」會誤判成「Glenorchy Lagoon Scenic Walkway」的重複
